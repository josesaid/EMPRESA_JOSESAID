Manual de EMPRESA_JOSESAID

Este manual explica qué es cada pieza del sistema, para qué sirve y cómo se conecta con las demás. Está pensado para quien va a operar, probar o mantener la plataforma, aunque no haya escrito el código.

La plataforma tiene 9 microservicios de área, un gateway de entrada, un servidor de registro y herramientas de monitoreo y trazabilidad. Cada color de este manual representa un área.

  • Ventas y clientes
  • Finanzas
  • Operaciones y compras
  • Legal
  • Dirección
  • Acceso
  • Infraestructura

2. Servicios de área

Cada servicio es dueño de sus datos y tiene su propia base de datos en PostgreSQL. Ningún servicio lee la base de otro: se comunican por la API o por eventos de Kafka.

Ventas y clientes

clientes-ms · 8101

Clientes

Guarda los datos de cada cliente. Los datos sensibles se cifran antes de guardarse, y se busca por un índice protegido para no exponer el valor original.

Requiere las claves CRYPTO_CLAVE_CIFRADO y CRYPTO_CLAVE_INDICE en su propio archivo .env.

pedidos-ventas-ms · 8107

Pedidos y ventas

  • Cotizaciones: borrador, enviada, aceptada o vencida.
  • Pedidos: borrador, confirmado, entregado, cancelado o devuelto.
  • Totales con IVA general (16 %), fronterizo (8 %) y exento.

Una cotización vencida no se puede aceptar: responde 410.

Finanzas

facturacion-pagos-ms · 8103

Facturación y pagos

Emite facturas y registra los pagos que las cubren.

contabilidad-ms · 8104

Contabilidad

Registra las pólizas contables. Los movimientos se guardan para no alterar el histórico.

Operaciones y compras

inventario-operaciones-ms · 8105

Inventario

Controla existencias y movimientos de almacén. Las cantidades usan tres decimales.

compras-proveedores-ms · 8106

Compras y proveedores

Administra proveedores y órdenes de compra. El RFC del proveedor se muestra enmascarado y los datos sensibles van cifrados.

Usa COMPRAS_CIFRADO_CLAVE e COMPRAS_INDICE_CLAVE.

Legal

documentos-cumplimiento-ms · 8108

Documentos de cumplimiento

  • Guarda contratos, permisos y registros legales en versiones.
  • Los archivos se cifran con AES-256 antes de escribirse en disco.
  • Calcula el tiempo de retención según el tipo de documento.
  • Una tarea diaria a las 7:00 avisa de los documentos por vencer.

Las versiones no se pueden modificar: una base de datos lo impide.

Dirección

reportes-ejecutivos-ms · 8109

Reportes ejecutivos

  • Consolida los indicadores de todas las áreas por periodo.
  • Marca como desactualizado un indicador cuya fuente no se actualizó en 7 días.
  • Al cerrar un reporte se guarda una foto que ya no cambia.
  • Exporta en CSV, PDF y XLSX.

Recibe los indicadores de las áreas por el tópico indicadores-areas.

Acceso

usuarios-accesos-ms · 8102

Usuarios y accesos

Emite los tokens JWT que usan todos los servicios para saber quién hace cada solicitud y qué rol tiene. Los roles son ADMIN, FINANZAS, CONTADOR, VENTAS, COMPRAS, ALMACEN, OPERACIONES, CALIDAD, DIRECCION y LEGAL.

Todos los servicios usan el mismo USUARIOS_JWT_SECRET.

3. Infraestructura

postgres

PostgreSQL 17

Una base de datos por servicio, creada al iniciar por infra/postgres/init-databases.sh. Si el volumen ya existía, la base y el rol se crean a mano.

kafka

Kafka

Transporta los eventos entre servicios. Cada servicio publica en su propio tópico, por ejemplo clientes.eventos.v1 o compras.eventos. Reportes consume el tópico indicadores-areas.

Kafka UI (http://localhost:8090) muestra los tópicos y sus mensajes. Un tópico aparece en cuanto recibe su primer evento.

discovery-ms · 8761

Registro de servicios (Eureka)

Cada servicio se registra al arrancar. Su panel muestra qué está en línea. Si este registro se levanta después, los servicios aparecen solos en menos de un minuto.

gateway-ms · 8080

Gateway

Recibe todas las solicitudes y las reenvía al servicio correcto. Cada servicio registrado queda en /{nombre-del-servicio}/.... Por ejemplo, /usuarios-accesos-ms/v1/auth/login.

No valida tokens: cada servicio lo hace.

prometheus · 9090

Prometheus

Lee cada 15 segundos las métricas de todos los servicios, como tiempos de respuesta, memoria y solicitudes.

grafana · 3000

Grafana

Muestra las métricas en tableros. Entra con el usuario admin y la contraseña de GRAFANA_ADMIN_PASSWORD.

jaeger · 16686

Jaeger

Muestra el camino de cada solicitud: por qué servicios pasó y cuánto tardó en cada uno. Se busca por servicio en Find Traces.

4. Cómo viaja una solicitud

Cliente o aplicación→ gateway-ms (8080)→ servicio de área→ su base de datos

El servicio de área valida el token JWT y revisa el rol. Si la operación cambia datos y debe avisar a otras áreas, guarda el evento en su tabla outbox_eventos dentro de la misma transacción. Un proceso lo envía después a Kafka. Así un evento nunca se pierde aunque Kafka esté caído en ese momento.

Las solicitudes quedan registradas en Jaeger de principio a fin, y sus métricas llegan a Prometheus.

5. Orden para levantar todo

  1. Red y base: docker network create empresa-net (una sola vez), luego docker compose up -d postgres kafka.
  2. Registro: docker compose up -d discovery-ms. Los servicios deben encontrarlo al arrancar.
  3. Gateway y servicios de área: docker compose up -d --build desde la raíz. Pueden levantarse en cualquier orden entre sí.
  4. Monitoreo y trazas: ya quedan incluidos en el mismo comando.

Cada servicio también puede levantarse solo desde su carpeta. Su README indica qué necesita antes.

6. Dónde revisar que todo funciona

  • Servicios registrados: http://localhost:8761
  • Salud a través del gateway: http://localhost:8080/usuarios-accesos-ms/actuator/health
  • Objetivos de métricas: http://localhost:9090/targets
  • Tableros: http://localhost:3000
  • Trazas: http://localhost:16686

Antes de empezar: cada servicio necesita sus variables en el .env de la raíz o en el suyo. Si falta una, Docker Compose lo indica con un mensaje que empieza por Defina. Guarde las claves de cifrado: sin ellas no se pueden leer los datos cifrados.

7. Glosario

Microservicio
Programa pequeño que hace una sola cosa de negocio y tiene su propia base de datos.
Gateway
Punto de entrada único que reenvía cada solicitud al servicio correcto.
Eureka (discovery)
Registro donde cada servicio se anuncia para que los demás lo encuentren.
JWT
Token firmado que identifica al usuario y su rol. Lo emite usuarios-accesos-ms.
DDD
Diseño guiado por el dominio: el código se organiza según los conceptos del negocio, como Cotización o Reporte.
Outbox
Tabla donde un servicio deja los eventos que debe publicar, dentro de la misma transacción que el cambio de datos.
Flyway
Herramienta que aplica los cambios de la base de datos en orden y una sola vez.
RFC 9457
Formato estándar de los errores de la API: indica tipo, título, estado y detalle.
Trazas (OTLP)
Protocolo con el que los servicios envían sus trazas a Jaeger.
Métricas (Prometheus)
Números que describen el estado de cada servicio: memoria, solicitudes y tiempos.

8. Lo que falta por decidir

  • Validación de tokens centralizada en el gateway.
  • Acceso por área en reportes: hoy solo ve todo el rol DIRECCION.
  • Autenticación en el panel de Eureka y en las métricas.
  • Retención documental (años por tipo) y purga física al vencer, pendientes de confirmación legal.
  • IVA fronterizo del 8 % pendiente de validar con Contabilidad.

9. Endpoints y ejemplos JSON por microservicio

Cada bloque lista las rutas de un servicio y un cuerpo de ejemplo para probarlas. Por el gateway, la ruta lleva el nombre del servicio al inicio: http://localhost:8080/clientes-ms/v1/clientes. También se puede llamar directo al puerto del servicio (sección 1): http://localhost:8101/v1/clientes.

Todas las rutas, salvo el login, piden el encabezado Authorization: Bearer <token>. Los ejemplos usan un UUID de prueba, 3fa85f64-5717-4562-b3fc-2c963f66afa6: reemplácelo por el id real que devuelve cada creación.

Formatos: fecha 2026-10-29, instante UTC 2026-10-29T16:30:00Z, mes o periodo 2026-10. Los errores siguen RFC 9457 (campos type, title, status y detail). Los campos que no aparecen como obligatorios pueden omitirse.

Primer paso: obtener el token

curl -s -X POST http://localhost:8080/usuarios-accesos-ms/v1/auth/login \
  -H "Content-Type: application/json" \
  -d '{"correo":"admin@empresa.mx","password":"<su-contraseña>"}'

La respuesta trae accessToken, tokenType y expiresIn. Ese valor va en el encabezado Authorization de las demás llamadas.

GET/v1/documentos/{id}Consulta el documento y sus versiones. Nunca muestra la ruta de almacenamiento.
GET/v1/documentos/{id}/versiones/{n}/descargaDescarga la versión n.
GET/v1/documentos/por-vencer?dias=30Documentos que vencen en los próximos días.
POST/v1/documentos/{id}/eliminacionMarca el documento para eliminación con un motivo.
GET/v1/catalogos/tipos-documentoTipos de documento y su retención en años.
tipo
CONTRATO, PERMISO, REGISTRO_LEGAL

Las versiones no se pueden modificar.

Subir un documento (curl)

curl -X POST http://localhost:8080/documentos-cumplimiento-ms/v1/documentos \
  -H "Authorization: Bearer $TOKEN" \
  -F 'datos={"tipo":"CONTRATO","titulo":"Contrato marco de servicios 2026","area":"Administración y legal","venceEn":"2027-12-31"};type=application/json' \
  -F "archivo=@/ruta/al/contrato.pdf"

Agregar una versión (curl)

curl -X POST http://localhost:8080/documentos-cumplimiento-ms/v1/documentos/{id}/versiones \
  -H "Authorization: Bearer $TOKEN" \
  -F "archivo=@/ruta/al/contrato-v2.pdf"

Solicitar eliminación

POST /documentos-cumplimiento-ms/v1/documentos/{id}/eliminacion
{
  "motivo": "Reemplazado por una versión nueva"
}

MétodoRutaPara qué

GET/v1/indicadores?periodo=2026-10&area=Consulta indicadores por periodo. El filtro area es opcional.

VENTAS_ATENCION_CLIENTES, FINANZAS_CONTABILIDAD, OPERACIONES, COMPRAS_PROVEEDORES, ADMINISTRACION_LEGAL, DIRECCION_GENERAL

CSV, PDF, XLSX

Registrar un indicador

POST /reportes-ejecutivos-ms/v1/indicadores
{
  "area": "OPERACIONES",
  "nombre": "Órdenes cerradas",
  "periodo": "2026-10",
  "valor": 12.5,
  "fuenteActualizadaUtc": "2026-10-29T10:00:00Z"
}

curl -o reporte.pdf "http://localhost:8080/reportes-ejecutivos-ms/v1/reportes/{id}/exportacion?formato=PDF" \
